# Mithtech kit (v{{VERSION}}): rules for every session. Kit folder: {{KIT}} (`<kit>` in skills).
- READ FIRST: project CLAUDE.md, then HANDOFF.md, then only the docs your task needs. If the repo has its own coordinator/brief/contract workflow (for example FieldOps, merqPOS), follow it.
- REUSE FIRST: before building, check the project index (`.claude/index/`), the Mithtech catalogue (`<kit>/../catalog/`), installed apps/modules/plugins and built-in platform features. If it exists or is easy to extend, STOP: tell me what and where, with extend-or-rebuild advice.
- SINGLE SOURCE OF TRUTH: every master record and setting has one owner (an existing DocType, module or table). Never create a duplicate DocType, model, field, table or setting; link to the owner instead of copying.
- NAMING AND LAYERING: Frappe apps `framith_<name>`, Medusa plugins `mithusa-<name>`. Build generic, setting-driven apps first; each customer gets one customer app for their customisations only. Other customers could use it: generic app behind a setting; else customer app. Say which and why.
- PLACEMENT: code goes in the existing app/module/plugin/crate that owns the domain. State where and why, with one alternative. A new app, module, plugin or service needs my yes.
- GATES: size every task. S (bug fix, one field, small change, pattern match): one-line reuse check, then build. M (one feature): CONFIRM FIRST, reuse check, then ONE mini pack (placement, data changes existing vs new, wireframe if a page changes, test plan, token estimate) for my yes. L (module, app, program): use the orchestrate skill. Build only what was approved, and all of it.
- PATTERNS: if a task matches a recipe in `<kit>/patterns/`, follow it and skip planning.
- ROUTING: load the stack skill (frappe-dev, medusa-dev, nextjs-js, rust-dev, other-stack) plus enterprise-core for business logic. Multi-session work: orchestrate. Model/effort: `<kit>/routing.json`.
- TOKENS: grep the index before reading code; read only the lines you need; never re-read unchanged files; show diffs, not full files; never echo code; write briefs, not pasted code; targeted tests while working, the full gate once; no speculative features or extra dependencies.
- SAFETY: never force-push or push to main/master/production unless I ask. Production deploys and production data changes need my explicit yes, every time. Back up before migrate. Never edit vendored or upstream code (frappe, erpnext, hrms, india_compliance and other third-party apps, @medusajs core, node_modules, generated code). Never copy databases between machines without asking.
- DONE = the project's gate passes, every approved requirement is built and tested, no stub or mock on a feature claimed done, status updated.
- RUNNING APPS: follow the coding root CLAUDE.md (Offload) when present.
- COMMUNICATION: answer first. Label blocks **Telling** (facts, results, recommendations) and **Asking** (one question). At most 10 lines unless I ask for detail. No narration, no recap of what I said, no repeated questions.
- QUESTIONS AS OPTIONS: ask with AskUserQuestion whenever it is available: 2-4 options, the recommended one first and marked (Recommended), short labels. Plain text only when the tool is unavailable (headless runs).
- CONFIRM FIRST (M and L): before any work, restate the request in at most 7 bullets: Goal, In scope, Out of scope, Placement, Assumptions (only ones you cannot check), Done when. Ask me to confirm with options (Correct / Change something). Skip for S.
- WRITING STYLE (ASD-STE100 rules, no restricted dictionary): one idea per sentence; instructions max 20 words, descriptions max 25; active voice; instructions start with a verb; one term per meaning, used the same way every time; no noun clusters of more than 3 words. Applies to messages, briefs, packs and reports; not to code or logs.
- FINAL REPORT (max 8 lines): branch, commits, gate result, deploy status, pending items, risks, tokens used vs budget.
- LESSONS: after a fixed bug or a program, record kit-gap and stack-gotcha lessons with `node <kit>/scripts/contribute.mjs lesson ...` (see the checker agent).
