# Mithtech kit v{{VERSION}}: rules for every session. Kit folder `<kit>` = {{KIT}}. Ids: <kit>/rules.json; stack rules load with their skill.
- SESSION START: E17 At session start, read the project CLAUDE.md, then HANDOFF.md, then only the docs the task needs. Follow the repo's own coordinator, brief or contract workflow when it has one (for example FieldOps, merqPOS). E18 When a task matches a recipe in `<kit>/patterns/`, follow it and skip planning. E19 Before you change code, load the stack skill. Also load enterprise-core when the change touches business rules or data. Use the orchestrate skill for multi-session work. E20 Before you start a session, worker or subagent, get its model and effort from `node <kit>/scripts/route.mjs <route-id|describe:work> [--floor id]`. Pass both on the call. E21 To run an app, follow the coding root CLAUDE.md (Offload) when it exists.
- REUSE: E01 Before you build, check the project index, the catalogue (`<kit>/../catalog/`), installed apps, modules, plugins and components, and built-in features. If something exists or extends easily, stop: say what and where, and advise extend or rebuild. N01 Add no new framework or dependency without approval.
- SINGLE OWNER: E02 Give every master record and setting one owner: an existing DocType, module or table. Link to the owner; never copy it or create a duplicate DocType, model, field, table or setting.
- PLACEMENT: E03 Put code in the existing app, module, plugin or crate that owns its domain. State where and why, with one alternative. E23 Get approval before you create a new app, module, plugin or service. E16 Build the generic, setting-driven app first. Put a change other customers could use in the generic app, behind a setting. Put every other change in that customer's one customer app. Say which and why.
- TASK SIZE AND APPROVALS: E04 Size every task before you start. S (bug fix, one field, small change, pattern match): do a one-line reuse check, then build. M (one feature): confirm it (C01) and check reuse. Then get approval for one mini pack: placement, data changes (existing or new), wireframe and flow if a page changes, test plan, token estimate. L (module, app, program): use the orchestrate skill. E05 Build everything that was approved, and nothing that was not. E24 Show the full item in chat with every approval request: pack, wireframe, diff, contract change or screenshot. A path or summary is not enough; relay a worker's pack in full. E08 Get explicit approval before every production deploy and every production data change.
- SCREENS AND UI: E14 For a task that adds or changes a screen, get three approvals, in order. 1: wireframe. 2: software flow (Mermaid: screens, actions, states, roles, errors, empty and loading). 3: UI/UX review against TonalDepth (layout, accessibility, light and dark, mobile). Build only after all three. Show screenshots next to them at each UI milestone. A screen change re-opens only the affected approval. E25 Build every UI with TonalDepth (`<coding root>/tonaldepth`, npm `@mithtech-bengaluru/tonaldepth-*`): its tokens, Mithtech colours, subtle claymorphism, light and dark modes. Use no raw colours and no outline-only depth. Copy this rule into every UI brief.
- GIT AND GITHUB: E07 Never force-push. Never push to main, master or production. Put work on main only through a pull request, for example `git ship`. E12 Use only free GitHub features: no Actions, required status checks, Codespaces or Copilot. Before every pull request, run the gate locally or on the home cluster (Offload), and put the result in the PR body. E13 With live git sync on (`<kit>/docs/two-macs.md`), work on `wip`. SessionStart pulls it, Stop pushes it after each turn, and a job syncs idle repos. When SessionStart says PAUSED, help clear it first. Never commit a `*.sync-conflict-*` file.
- SECRETS: E10 Read secrets and configuration from environment variables. Keep secrets out of git, images, logs and shared files.
- DATABASES: E28 Back up the database before every migration. E11 Never copy a database between machines without asking.
- THIRD-PARTY CODE: E09 Never edit vendored code: frappe, erpnext, hrms, india_compliance, other third-party apps, our forks of them, @medusajs core, node_modules, generated code.
- TESTING AND DONE: E29 Run targeted tests while you work, and the full gate once before you push. E06 Call a task done only when its gate passes locally and every approved requirement is built and tested, with no stub or mock. Then update the status. E26 Before a test that drives or captures the screen, move every monitor to an empty desktop (Mission Control). Never test over open windows. Copy this rule into every GUI-test brief. E30 After you fix a bug or finish a program, record lessons with `node <kit>/scripts/contribute.mjs lesson ...`.
- TOKENS: E22 Grep the index before you read code. Read only the lines you need, and never re-read an unchanged file. E31 Show diffs, not full files; never echo code. Write briefs in words, not pasted code.
- COMMUNICATION: C02 Answer first. Keep a message to 10 lines unless asked for detail. Do not narrate, recap the request or repeat a question. C07 Label message blocks **Telling** (facts, results, recommendations) and **Asking** (one question). C01 Ask one question at a time: 2 to 4 options with short labels, the recommended one first and marked (Recommended), with AskUserQuestion when available. Before an M or L task, restate it in at most 7 bullets: goal, in scope, out of scope, placement, assumptions you cannot check, done when. Then ask: Correct / Change something. C04 Write one idea per sentence. Keep instructions under 20 words and descriptions under 25. Apply C04 to C06 to messages, briefs, packs and reports, not to code or logs. C05 Use active voice. Start every instruction with a verb. C06 Use one term for one meaning, every time. Avoid noun clusters of more than 3 words. C08 End a task with a report of at most 8 lines: branch, commits, gate result, deploy status, pending items, risks, tokens used vs budget.
